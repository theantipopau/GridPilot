# TT Program: Recommended Next Build

## Current position

The project has completed data discovery, a proposed normalized model, ingestion and cross-validation, a read-only timetable grid, and composite-class detection. The next milestone should be a deterministic analysis engine. AI-generated advice should only consume validated findings from that engine.

## Immediate corrections

1. **Move `tester.tfx` out of version control or replace it with a fully synthetic fixture.** Even if it is currently blank, allowing a `.tfx` exception creates a future privacy risk if the file is replaced with live data.
2. **Do not store staff or student names in finding payloads.** Rules should use internal IDs and codes. Names should be joined only when rendering an authorized local view.
3. **Treat composite classes as reviewable configuration.** Detection should produce candidates. A user-approved record should determine whether clashes, load and utilization checks suppress the duplicate entries.
4. **Do not infer calendar dates from ISO week parity.** Store an explicit A/B-cycle calendar mapping because school calendars can be interrupted by holidays, pupil-free days and timetable changes.
5. **Separate source truth from proposed changes.** Keep imported records immutable and represent every draft move as an overlay or change set.

## Milestone 1: Finding framework

Create a common structured finding model:

```python
@dataclass(frozen=True)
class Finding:
    id: str
    rule_id: str
    severity: Literal["info", "warning", "critical"]
    title: str
    entity_refs: tuple[EntityRef, ...]
    slot_refs: tuple[SlotRef, ...]
    evidence: dict[str, object]
    suggested_actions: tuple[ActionCandidate, ...] = ()
```

Every rule should be deterministic, independently testable and return findings without prose generated by AI.

### First rules

- `teacher_double_booking`
- `room_double_booking`
- `student_double_booking`
- `room_capacity_exceeded`
- `room_feature_mismatch`
- `teacher_daily_overload`
- `teacher_consecutive_load`
- `teacher_free_period_fragmentation`
- `room_underutilization`
- `uneven_subject_spread`

Each rule needs fixtures for: normal case, genuine issue, composite-class exemption, missing capacity, missing teacher/room, and non-teaching entry.

## Milestone 2: Human-reviewed composite classes

Add:

- `composite_candidate`
- `composite_group`
- `composite_group_member`
- `review_status`: pending, approved, rejected
- reviewer timestamp and optional local note

Do not suppress a clash while a candidate remains pending. The UI should show supporting repeated slots and permit approval or rejection.

## Milestone 3: Safe change sets

Represent proposed edits separately from the imported timetable:

- `change_set`
- `proposed_change`
- before and after values
- originating finding IDs
- validation state
- approval state

A change set should support validate, compare, approve, reject and export. It should never mutate the imported source snapshot.

## Milestone 4: Constraint-based suggestions

Before Ollama, generate candidate moves algorithmically:

1. Find alternate rooms or periods satisfying hard constraints.
2. Reject candidates that create teacher, room or student clashes.
3. Reject room-capacity and room-feature failures.
4. Score remaining options using soft constraints such as movement, timetable spread, room utilization and staff load.
5. Give the ranked candidates and evidence to the local AI only for explanation.

This prevents the language model from inventing timetable changes.

## Milestone 5: Privacy and audit controls

- Synthetic fixtures only in Git.
- Local database and exports excluded from Git.
- No PII in application logs, test snapshots or exception traces.
- Local authentication or an explicit single-user desktop mode.
- Audit event for imports, rule runs, composite approvals, change-set approval and exports.
- Automatic source-file hash and import timestamp to prove which timetable version was analyzed.
- Configurable data-retention and purge action for working databases and exports.

## Milestone 6: Export gate

An export must not be labelled ready unless it passes:

- JSON/schema validation
- identifier and referential-integrity validation
- source-versus-output structural comparison
- unchanged-record fidelity check
- no newly introduced clashes
- approved-change-set reconciliation
- changelog generation
- backup and timestamped output filename

Initially, keep export behind an experimental flag and test re-import against a non-production copy of Timetabling Solutions.
